## 1. 创新点（第二批）

### I7 · 应用自身的失败可见性

**这是第二批里最"该做"的一条，因为它是唯一一条把工具的哲学用在工具自己身上的改动。**

DropQTT 的立身之本是"失败不许看起来像成功"（README 第一屏）。但**它自己的失败目前完全不可见**：
全仓没有 `panic::set_hook`、没有 `env_logger`、没有 `tracing`（`[读码]` 三者零命中）。
一个 panic 之后，用户能拿到的只有操作系统那句"已停止工作"，以及一个同样没有线索的 issue。

**形态**（三个零件，都能复用已有资产）：

| 零件 | 复用什么 |
| --- | --- |
| panic hook 捕获 panic 信息与 backtrace | 新增，但只十几行 |
| **有界环形日志**（最近 N 条 + 级别 + 时间戳） | 与 feed 缓冲同一套"有界 + 显式丢弃计数"的写法（§3.3 A2 的先例） |
| 并入**诊断包导出** | §4.44 环境包 + 诊断快照已经存在，只是不含运行时日志 |

**硬约束（不能妥协）**：日志与诊断包导出**必须走同一套脱敏**——
现在的红线是"secret 不落盘、不进日志、不进导出"，加了日志就有了新的泄漏面。
具体：日志里不得出现 payload 全文、broker 地址、webhook URL、clientId、文件路径中的用户名。
建议直接复用 I6 的 `Verdict` 思路：**日志行本身就是一个需要声明自己脱敏过的对象**，
而不是"记得别打"。

**诚实的边界**：环形缓冲会丢日志，丢了多少要计数并显示在导出里——
否则"日志里没有"会被读成"没发生过"，这正是 A2 那条修过一次的同类错误。

### I8 · 证据完整性总账

现在"损失"分散在四处，没有一处能回答"我刚看的这个结论，建立在多少完整的证据上":

| 计数器 | 含义 | 现状出口 |
| --- | --- | --- |
| `history.lost_rows` | 写库失败 | 诊断 + 指标 `history_lost_rows_total` |
| `history.pruned_rows` | 保留策略裁掉 | `[读码]` 有记账，**无 UI 出口、无指标** |
| `feed_lost` | 过载时连归档队列都满了 | 诊断 + 指标 `feed_lost_total` |
| `truncated` | 单行被截断存储 | 行级标志，逐条可见，但**没有全局计数** |

加上 UI 侧的 `feedDropped`（显示缓冲丢弃，只是看不见，不丢证据）——
**五者语义各不相同，混在一起谈"丢了多少"一定会错。**

**做成一个视图 + 一组指标**：在运维诊断里给一张"证据完整性"卡，按上述五类分列，
并明确每类意味着什么（"看不见但已存" / "确实没存下" / "存了但是残的"）。
它是 I6 `Verdict.caveats[]` 最自然的填充来源：一条结论若建立在被裁过的区间上，
就应该自动带上这个 caveat。

### I9 · `$SYS` 方言可插拔

`utils/sysDialect.ts` 已有厂商指纹与方言处理，且有 `sys-dialect.spec.ts` 钉着（`[读码]`）。
把它做成**用户可编辑/可贡献的表**：

- 未知 broker 不再是"什么都不显示"，而是明说"我们认出这些字段，其余的留空"——
  沿用 §4.31「读过的布局才用，没读过的就直说」这个已经确立的口径。
- 支持新 broker 从改代码变成加一条配置。对一个单人项目，这是把维护成本外包给社区的正确接口。
- 导出/导入方言表，随环境包走。

### I10 · 编解码注册表 + 候选新格式

现在 9 种视图（`auto`/text/json/senml/cbor/base64/hex/markdown/html）是硬编码分散在
`payload.ts` / `codec.ts` / `senml.ts` / `cbor.ts`（411 行）里的（`[读码]`）。
做成注册表之后，新格式是一个条目而不是一次散弹式改动。

候选格式（**成本差异极大，分开评估**）：

| 格式 | 成本 | 建议 |
| --- | --- | --- |
| **MessagePack** | 低——与 CBOR 同族，已有 411 行零依赖 CBOR 编解码器可作参照 | **建议做** |
| UBJSON | 低 | 顺带 |
| **Sparkplug B**（`spBv1.0`） | **高**——payload 是 protobuf，需要内置 schema 与 birth/death 语义 | **先做需求调研，不要直接动手** |

Sparkplug 在工业 IoT 里很常见，但"支持 Sparkplug"的正确形态远不止一个解码器
（还有 BIRTH/DEATH 序列、alias 映射、metric 时序），**做一个半吊子解码器会给出一个看起来对、
实际上缺了序列语义的视图**——这恰恰是本项目最反对的那类东西。建议先调研再决定。

## 2. 需求点（第二批）

- **R11 CLI 随产物分发**。`release.yml` 里没有任何 CLI 构建（`[读码]` 零命中），
  所以 CLI 只有"自己 clone + 装 Rust 工具链"这一条获取途径。
  而 README 自己写着"**一个和自己 GUI 说法不一致的 CLI，比没有 CLI 更糟**"——
  **当前的分发方式恰好保证它一定会漂移**：用户 clone 到的 commit 与他装的 GUI 版本无关。
  两条路（可任选）：① release 里挂 `dropqtt-cli-<target>`；② 退一步，
  让 CLI 输出里始终带自己的版本与构建 commit，`verify --json` 里也带，
  这样 CI 至少能**校验**两者一致，而不是只能相信。

- **R12 时间与时区** `[读码]`。界面用 `toLocaleTimeString()` / `toLocaleString()`
  （`HistoryPanel.tsx:52-53`、`FieldProbeCard.tsx:7`、`TimelineCard.tsx:32`），
  导出用 `toISOString()`（UTC，`exportMessages.ts:35/86`、`HistoryPanel.tsx:305/378/394`）。
  **同一个时刻在两处长得不一样，且界面不标注时区。**
  对一个取证工具这是硬伤：跨时区协作、对照设备日志、对照 broker 日志时必然错位。
  建议：全局"UTC / 本地"切换（默认本地，可切 UTC）、任何显示时刻处带时区标注、
  导出一律带 offset。这一条与 O12 可以一起做。

- **R13 发送/接收前磁盘空间预检**。60 MB 真机测过（`[文档]` §4.10），更大没测；
  接收端落盘前不检查可用空间，中途失败比开局失败难处理得多。低成本，且符合
  "失败要在最便宜的地方发生"这个项目的既有取向。

- **R14 历史库 + outbox 库的运维出口** `[读码]`。
  两个 SQLite：`dropqtt_history.db`（`lib.rs:853`）与 outbox 那一份（`outbox.rs` 用 rusqlite）。
  两者都没有"在哪 / 多大 / 能不能搬 / VACUUM"的出口。
  尤其 outbox（§4.48 的死信队列）——**死信会累积，而用户看不到它在长**。

- **R15 应用内 Release Notes**。updater 只给版本号；仓库根没有 CHANGELOG（`[读码]`）。
  用户看到"有新版本 0.11.3"但不知道值不值得更。最低成本形态：
  release.yml 生成时把 tag 的 release notes 打进 updater 的 `notes` 字段。

- **R16 实时流的无障碍策略**。feed 每秒数百条，`aria-live` 直接播报会刷屏甚至卡死读屏软件；
  但完全不播报，视障用户就根本拿不到实时流——**而"拿不到"和"没有"在这个项目里必须区分**。
  需要一个显式策略（例如：节流成"新增 N 条"的摘要 + 用户可暂停 + 暂停状态可见）。
  这与 §4.53 量过的渲染成本是同一类张力，建议先量再定形。

## 3. 优化点（第二批）

> 性能类仍是**假设**，先量后改。

- **O11 `HistoryStore` 读写共用一把锁** `[读码]`。
  `open()` 返回 `conn: Mutex<Connection>`，单连接既写又读。
  而 `append()` 在 feed flush 路径上，`series()` **没有 LIMIT**（第一批 O2-1 已指出）——
  一个全量扫 10 万行的图表查询会**持锁直到扫完**，直接压住写入侧。
  **先量**：在满库（10 万行）上量 `series()` 的持锁时长，以及在压测下它是否让
  `lost_rows` 上涨。若成立，改法是读写分离（一个写连接 + 小读连接池），
  WAL 已经允许这个形状，改动集中在 `HistoryStore` 内部。
  **这是第一批 O2 的放大版**：O2 说"查询慢"，O11 说"查询慢会传导到写入正确性"。

- **O12 导出的时间戳与文件名三处各拼各的** `[读码]`。
  `exportMessages.ts:35/86`、`HistoryPanel.tsx:305`、`ScenarioPanel.tsx:82` /
  `EnvironmentCard.tsx:31` 各自 `new Date().toISOString()`，其中两处还各自做
  `.replace(/[:.]/g, '-')`。统一成一个 `exportStamp()`，顺便把 R12 的时区问题一次修掉。

- **O13 主题对比度自动化**。4 套主题 × 4 语言，对比度靠手调
  （`[文档]` §3.5 手工把 `--text-muted` 从 `#a8a29e` 改到 `#78716c` 就是一次事后修补）。
  加一个脚本：从 `themes/index.ts` 读 CSS 变量，算前景/背景的 WCAG 对比度，低于阈值即失败，进 CI。
  成本低，且把"浅色主题看不清"从人眼发现变成门禁发现。

- **O14 i18n"疑似未译"检测**。1032 键 × 4 语言。`ja` / `zhTW` 里若某个键的值与 `en`
  **完全相同**（且不在专有名词白名单里），很可能就是漏译。
  `check-i18n-parity.py` 已经同时加载了四份，加一个"疑似未译"报告很便宜。
  注意它只能给候选、不能自动判——误报要能白名单掉。

- **O15 CI 加 `schedule` / `timeout-minutes` / dependabot** `[读码]`。
  两个 workflow 都没有 `schedule`，也没有 `timeout-minutes`；`.github` 下没有 dependabot 配置。
  没有定时跑，依赖漂移与 flaky 只会在某次 push 上随机冒出来，归因困难；
  没有 timeout，一个卡住的作业会挂到 GitHub 的全局上限。
  建议至少加 `schedule`（每周一次）+ `timeout-minutes`。

- **O16 仓库卫生** `[读码]`。根目录 `PROJECT_ANALYSIS.md` 头部写着
  **v0.7.1 / 13,782 行 / 8 个模块**；现在是 **v0.11.2 / ~48k 行 / 25+ 个模块**。
  而 AGENTS.md 把新接手的人指向 `docs/` 下四份文档——这两份会打架。
  建议移到 `docs/archive/` 并在开头加一行"历史快照，不代表现状"，
  或直接删除（它记录的已修条目有价值，取舍**留给属主**）。

## 4. 安全与合规

- **S1 把"secret 不落盘"变成可执行测试。**
  现在这条红线靠纪律 + §4.3 / §4.75 的**手工**验证。建议加一个测试：
  用含已知 sentinel 的口令 / webhook header token 配一份配置，
  然后导出环境包、捕获文件、场景文件、诊断报告，**断言导出文本中不出现 sentinel**。
  这把"记得别写进去"变成"写进去就红"。
  成本很低，而且与 §4.84 的哲学完全一致——**教训要写成守卫，不是写进文档等人读**。
  （先验证：断言一个 sentinel 真的会被当前代码写进去时，测试必须变红。
  否则它就是又一个"永远通过的断言"。）

- **S2 收窄 `fs:default` 的具体路径。** AGENTS.md 已列为属主决定，这里只补实施顺序：
  ① 新增后端命令 `write_text_file`（限定在用户经对话框选择的路径）；
  ② `exportMessages.ts:61` 改走它；③ 再删 `fs:default`。
  **顺序不能反**——P1-4 那条审计建议的前提已被证伪（`exportMessages.ts:61` 确实在用 fs），
  先删权限等于静默砍掉导出功能。

## 5. 分发与社区

- **D1 包管理器分发**：Homebrew cask / winget / Scoop / AUR。
  对"临时装一个调试工具"这类场景，`brew install` 的转化明显高于下载 dmg，

  是否 TLS/mTLS、客户端 id），有一个模板能显著降低往返次数。

## 6. 测试方法论

- **T1 把两类已踩过的坑写成守卫**（与 §4.84 同一思路）：
  1. **"永远通过的断言"** —— §4.81b 抓到 `toHaveCount(0)` 对不存在的元素恒真。
     加一条 lint 或脚本规则：禁止裸 `toHaveCount(0)`，或要求先断言容器存在。
  2. **"跑不起来的检查"** —— §4.84 的 `check-ci-shell.py` 已经给了范本
     （计数不变式 + 缺文件算失败）。把同样的两条不变式套到
     `check-i18n-parity.py` 与 `check-release-ready.py` 上：
     它们是否也对"文件找不到"和"抽到的条目数变少"算失败？
     **一个静默少测的检查，报出的"无事发生"和通过长得一模一样。**

- **T2 变异测试半自动化。**
  本项目每次手工做变异（`[文档]` §4.80 / §4.81 / §4.82 / §4.85 都有实录），
  而且**每一次都抓到了洞**——价值已经被反复证明。
  可以先做一个最小脚本：对指定文件的指定常量/布尔做机械变异，跑指定测试，
  报告"哪些变异没被杀"。不追求通用，先把每次手工做的那几步记下来变成可重放。
  这比"每次靠记性做一遍"更可靠，也更符合"验证工具本身也要验"这条规矩。

## 7. 一个我不敢断言、只提请验证的疑点

### V1 · 两个实例同时跑会不会互踢

**这是疑点，不是结论。我没有跑过两个实例，不敢断言。**

事实依据 `[读码]`：

- 默认 clientId 是 `DropQTT_<8 位随机>`（`protocol.rs:102-108`），
  只在配置初始化时生成一次，之后随 `dropqtt_active_broker` / `dropqtt_broker_profiles`
  持久化（`useBroker.ts:33-34`）。
- 两个应用实例在 Tauri v2 下**共享同一个 WebView 数据目录**，因此共享同一份 localStorage
  → **同一个 clientId** → broker 会踢掉先连上的那个。
- 有意思的是：`test_broker_connection` **特意加了 `_t{6 位随机}` 后缀避免撞车**
  （`mqtt_manager.rs:487-489`），说明项目已经知道这个风险，
  **但正式连接没有同等保护。**
- 而 §4.10 的真机双端验证确实跑过两个实例并成功了——可能是当时手动改了 id，
  也可能两个实例的存储并不共享。**这正是需要验证的点。**

**建议的验证方式**（沿用项目规矩，别猜）：起两个实例，读各自 CONNACK 后的实际 clientId，
再观察 broker 侧的连接数与踢下线事件。**先验，再决定要不要改。**

如果成立，这是"同一个概念两套处理"的又一个实例（§4.85 已经为此删掉过一个重复的
`SysProbe` 状态机），修法应该是让正式连接也走已有的那套唯一化逻辑，而不是新造一个。
