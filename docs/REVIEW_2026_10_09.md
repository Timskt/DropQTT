## 0. 一句话总评

这是一个**纪律极其严明、工程素养远超多数单人项目**的代码库——"失败不许看起来像成功"不是口号，而是贯穿 81 个命令、48k 行代码、24+40 个测试文件的实测约束。它的短板不在代码质量，而在**信息架构**（五个工作区平铺、控制台面板堆叠）和**架构天花板**（单连接、无日志、核心状态机覆盖不足）。这两类问题的性质不同：前者是 UX 设计问题，后者是"单人项目该不该现在动"的取舍问题。

## 1. 前端界面与布局

### 1.1 控制台工作区的信息架构问题（提案未充分展开） `[读码]`

`App.tsx:548-701` 的控制台模式在一个纵向滚动容器里堆了 **12 个面板**：

```
SubscriptionsBar → MessageStream → BrokerSysPanel → TopicTrafficPanel
→ DevicePanel → AssertionPanel → FaultPanel → ResponderPanel
→ MessagePublisher → RpcPanel → ReplayPanel → ScenarioPanel
```

提案把这个问题归结为"capabilities 藏在折叠面板里，靠 Ctrl+K 命令面板补救"。**这是症状，不是病因。** 病因是控制台本身没有二级信息架构——它把**收发**（SubscriptionsBar / MessageStream / MessagePublisher / RpcPanel）、**观测**（BrokerSysPanel / TopicTrafficPanel / DevicePanel）、**仿真与验收**（FaultPanel / ResponderPanel / AssertionPanel / ScenarioPanel / ReplayPanel）三类不同心智模式的功能平铺在一条滚动轴上。

命令面板（`App.tsx:308-407`）确实缓解了发现性，但它是**对信息架构缺陷的补丁**，不是解决方案。一个首次使用者不会先学 Ctrl+K，他会先滚动——然后被 12 个面板淹没。

**建议**（与提案不冲突，提案没提这个）：控制台内部再分一层 tab 或分区——「收发 / 观测 / 仿真·验收」三组。这不需要改任何后端命令，只是 `App.tsx` 的 mqttx 分支内部加一层条件渲染 + 一个 tab state。成本小，感知大。

### 1.2 固定侧栏无折叠，窄窗口体验差 `[读码]`

`Sidebar.tsx:91` 写死 `w-60`（240px），无折叠、无响应式断点。主区域 `flex-1 min-w-0`（`App.tsx:435`）会收缩，但 240px 在 800px 窗口下占了 30%。README 声称"fluid container-driven layouts work at the default window size"——default window size 是关键词，窄窗口不在承诺范围内。

对一个桌面 MQTT 工具，用户常会把它缩到半屏对照 broker 日志。**建议**：侧栏加一个折叠态（只留图标列 ~48px），或用 CSS `@media` 在窄窗口下自动折叠。这是纯 CSS + 一个 `collapsed` state，不碰任何业务逻辑。

### 1.3 样式双轨制：className 与 inline style 并存 `[读码]`

全仓大量使用 `style={{ background: 'var(--bg-panel)' }}`（如 `Sidebar.tsx:92`、`App.tsx:455`、`ErrorBoundary.tsx:38`）。原因是主题靠运行时切换 CSS 变量，Tailwind JIT 无法在运行时改变量——**这个取舍是合理的**。但代价是样式散布在 `className`（Tailwind 工具类）和 `style`（CSS 变量）两套体系里，读代码时要同时看两处。

这不是 bug，但值得记录：**未来若引入 Tailwind v4 的 `@theme` 或 CSS-in-JS 方案，可以统一**。当前阶段不建议动——风险/收益不匹配。

### 1.4 ErrorBoundary 粒度只到工作区级 `[读码]`

`App.tsx:471` 用一个 `ErrorBoundary` 包住整个 `<main>`。`MessageStream`（1094 行、处理高频不可信 payload）内部某个 row 渲染抛错时，**整个控制台工作区**都会切到 fallback，用户丢失订阅状态视图、发布器等全部可用面板。

`ErrorBoundary.tsx` 本身设计是好的（`role="alert"`、可重试、显示 error.message）。问题是粒度。**建议**：在 MessageStream 的 row 渲染层再加一层细粒度 boundary，让单条坏 payload 只黑掉那一行，不波及整个工作区。成本是 ~15 行。

### 1.5 主题与对比度 `[读码]`

4 套主题（cyberpunk / obsidian / nord / solaris）用 CSS 变量驱动，语义色分 text/soft/border 三阶（`themes/index.ts:30-60`），这个设计是成熟的。提案 O13 建议把对比度检查自动化进 CI——**同意**，solaris（浅色）主题的 `--text-muted` 历史上手工调过一次（§3.5），说明靠人眼不可靠。

## 2. 功能与新需求

### 2.1 单连接是最大的架构天花板 `[文档+读码]`

`lib.rs` 单 client 槽，73 个命令隐含"只有一个连接"，`App.tsx` 单 `broker.isConnected` 就 23 处。提案 §3.5 量过改造面并标为架构决策。**我同意不该顺手做。**

但提案 I5（双 broker 一致性探针）是**聪明的折中**——只加第二个只读探针连接，不碰 73 个命令的语义，复用桥接已有的"任意 conn id"能力。**建议优先于完整多连接评估**，因为它回答的是企业用户会为此打开工具的那类问题（broker 迁移验收、ACL 漏配检测），而不是"我想同时看三个 broker"的广度需求。

### 2.2 保留值沿革已实现，僵尸 retain 是亮点 `[读码+文档]`

`RetainedCard.tsx` + `utils/retained.ts` + `history.rs` 的保留值 lineage 已落地（§4.88）。这是**别人没有的结论**：broker 从不告诉你一个 retain 值有多老，而这个工具能从历史里读出来。空 payload + retain=1 被正确识别为**删除**而非空值。这个功能的价值/成本比极高，是项目"事后取证"定位的典型体现。

### 2.3 提案中我特别认同的新需求

| 编号 | 名称 | 为什么认同 |
|---|---|---|
| **R12** | 时间与时区：UTC/本地切换 + 时区标注 | `[读码]` 界面用 `toLocaleTimeString`、导出用 `toISOString`（UTC），**同一时刻在两处长得不一样且界面不标时区**。对取证工具这是硬伤。 |
| **R1→已作废** | 保存的连接档位 | `[读码]` 第二批已更正：`useBroker.ts:33-34` 已有 profiles 持久化 + `withoutStoredSecrets` 脱敏。多连接的"便宜 80%"已兑现一半。 |
| **I7** | 应用自身的失败可见性 | `[grep]` 全仓零 `panic::set_hook` / `env_logger` / `tracing`。一个以"失败不许看起来像成功"为立身之本的工具，**它自己的失败目前完全不可见**——这是哲学上的缺口。 |
| **R4** | 定时任务持久化 + 启动恢复 | 后端调度器已上线（`scheduler.rs`），但任务只在会话内存活，重启不恢复。 |
| **S1** | "secret 不落盘"变成可执行测试 | 把靠纪律的红线变成门禁，与项目"教训要写成守卫"的哲学完全一致。 |

### 2.4 提案中我要补充或不同意的

**补充 R16（实时流无障碍）**：提案说"feed 每秒数百条，aria-live 会刷屏"。**补充**：当前 `MessageStream` 对实时流的无障碍处理需要确认——如果完全没有 `aria-live`，视障用户根本拿不到实时流；如果有且无节流，会卡死读屏。这是"拿不到"和"没有"必须区分的典型场景，建议先量再定形。

**对 O3（13 个轮询定时器）的补充**：`[grep]` 我数到 **14 处** `setInterval`（含 `HistoryPanel.tsx:252` 的 3s）。提案说"先量"——同意，但**补充一个低成本的结构性改进**：不可见工作区的轮询应降档或停止。当前 `useBridge(visible)` 传了 visible，但 `useAssertions` / `useRpc` / `useFaults` / `useResponder` 也都接收 `activeMode === 'mqttx'`，说明已有可见性门控的雏形——**但 `useTopicStats` 1s、`useBrokerSys` 的 timer 是否真的在离开控制台后停了，需要逐个确认**。

### 3.2 疑点（提案标为未验证，我同意先验）

**V1 两个实例互踢** `[读码+文档]`：默认 clientId `DropQTT_<8位随机>` 只在配置初始化时生成一次，之后随 localStorage 持久化。Tauri v2 下两个实例**共享同一 WebView 数据目录** → 同一 clientId → broker 踢掉先连的。有意思的是 `test_broker_connection` 特意加了 `_t{6位随机}` 后缀避撞（`mqtt_manager.rs:487-489`），**但正式连接没有同等保护**。

**我的判断**：这个疑点值得优先验证——如果成立，它是"同一个概念两套处理"的又一个实例（§4.85 已为此删掉过一个重复的 `SysProbe` 状态机）。验证成本极低：起两个实例读各自 CONNACK 后的 clientId。**先验，再决定要不要改。**

### 3.3 O10：refuse_oldest_pending_sub 可能怪错主题 `[文档]`

§4.85 挖出但主动未动——多个 SUBSCRIBE 挤在一起时，错误码被归因给"最早在飞的那个"，被误怪的好主题会被隔离、从此不再重放。项目自己写明"风险与收益不匹配"。

**我同意不动，但强烈支持提案的建议**：至少加一条**能失败的测试**把现状钉住，否则它会在某次改动里被顺手改坏。这完全符合项目"验证工具本身也要验"的规矩。

### 3.4 console.error 散布 ~20 处 `[grep]`

`[grep]` 在 `src/` 下找到约 20 处 `console.error/warn`（App.tsx 3 处、useBroker 5 处、usePersistentState 2 处、ErrorBoundary 1 处等）。对桌面应用，这些应走后端结构化日志——但后端目前**没有日志系统**（I7 要补）。在 I7 落地前，这些 console 调用是唯一的问题出口，不建议现在删。

## 4. 工程质量

### 4.1 超大文件（超过 ECC 800 行上限） `[读码]`

| 文件 | 行数 | 问题 |
|---|---|---|
| `mqtt_manager.rs` | **3759** | 核心状态机，只有 6 条单测。提案 O5 已指出。 |
| `BridgePanel.tsx` | **1312** | 单组件过大，应拆分为子面板。 |
| `MessageStream.tsx` | **1094** | 高频渲染面，职责过重（视图解析 + diff + 导出 + 复制 + replay + trace）。 |
| `types.ts` | 1093 | 类型定义集中，可接受但接近上限。 |
| `i18n/types.ts` | 1062 | 手写接口，O7 建议用 `typeof en` 派生。 |
| `MessagePublisher.tsx` | 975 | 接近上限。 |
| `HistoryPanel.tsx` | 866 | 接近上限。 |
| `SettingsModal.tsx` | 745 | 接近上限，应分 tab。 |
| `App.tsx` | 740 | 上帝组件，承担过多编排。 |

**重点**：`mqtt_manager.rs` 3759 行 / 6 条单测是**风险与覆盖最不匹配**的地方。这 6 条单测覆盖的是流量统计与路径清理（`topic_traffic_*` / `sanitize_*`），而**订阅隔离/重放（§4.85 出过 bug）、feed 归档队列（A2）、传输状态机（§4.13 出过竞态）**这三类恰好是历史上真出过问题、又没有自动化回归的地方。

### 4.2 App.tsx 是上帝组件 `[读码]`

`App.tsx` 740 行里调用了 **18 个 hook**（useBroker / useBridge / useMqttMessages / useSubscriptionStats / useTopicStats / useBrokerSys / useHistoryCount / useTransfers / useBatchSender / useRpc / useAssertions / useFaults / useResponder / useBrokerCapabilities / usePersistentString ×5），定义了所有事件处理器、命令面板命令列表、所有工作区的条件渲染。

hooks 拆分是好的——逻辑确实被抽走了。但 **App.tsx 本身仍是唯一的编排中心**，任何新功能都会往这里加。这不是紧急问题，但如果下一轮要做多连接或控制台分 tab，App.tsx 会先成为瓶颈。

### 4.3 79 个命令的手写 IPC 双份 `[文档]`

Rust 侧 81 个 `#[tauri::command]`，前端侧手写 `invoke('command_name', { ... })`，无类型安全。提案 O8 建议要么上 `ts-rs` 全量类型化，要么生成一份 `命令名 → (参数名, 返回类型)` 清单由 CI 校验。AGENTS.md 把这条列为"留给属主决定"。

**我的补充**：项目已有的"退化成没有后端而不是报错"套路（`useMetrics` / `secrets.ts`）是聪明的——它让 19 个 spec 免了补桩税。但这恰恰说明**前端对后端命令的假设是散布在各个 hook 里的**，一个命令签名改了，前端不会在编译期知道。O8 的"便宜形态"（只生成清单 + CI 校验一致性）性价比最高。

### 4.4 i18n 维护成本 `[读码]`

1056 键 × 4 份语言文件 + 1 份手写 `Translations` 接口 = **五处要同步**。`scripts/check-i18n-parity.py` 做三方核对（四份文件 + 接口），门禁是有效的。但 O7 的建议——改成 `export type Translations = typeof en`——能消除"接口写对了但四份文件漏一个"这类错误的一半来源，且不影响门禁强度。**半天成本，建议做。**

### 4.5 没有 CHANGELOG / 应用内 Release Notes `[grep+文档]`

`[grep]` 仓库根无 CHANGELOG。updater（`App.tsx:250-270`）只给版本号，用户看到"有新版本 0.11.3"但不知道值不值得更。R15 建议把 tag 的 release notes 打进 updater 的 `notes` 字段——成本极低。

### 4.6 PROJECT_ANALYSIS.md 停在 v0.7.1 `[读码]`

根目录 `PROJECT_ANALYSIS.md`（72KB）头部写着 v0.7.1 / 13,782 行 / 8 个模块；现在是 v0.11.2 / ~48k 行 / 25+ 模块。AGENTS.md 把新接手者指向 `docs/` 下四份文档——**这两份会打架**。建议移到 `docs/archive/` 并加"历史快照"标注，或删除。取舍留给属主。

## 5. 安全

### 5.1 红线靠纪律，未变成可执行测试 `[文档+读码]`

项目的安全红线很清晰（AGENTS.md）：secret 不落盘、不进日志、不进导出；密码进 OS keyring 只存 `secretRef`；mTLS 材料缺失硬失败；指标端点只绑 loopback 且不含敏感标签。

**但这些靠纪律 + 手工验证**（§4.3 / §4.75）。提案 S1 建议加一个测试：用含已知 sentinel 的口令配置一份配置，导出环境包/捕获文件/场景文件/诊断报告，**断言导出文本中不出现 sentinel**。**强烈同意**——这把"记得别写进去"变成"写进去就红"，与项目哲学完全一致。

**关键前提**（提案也强调了）：先验证 sentinel 真的会被当前代码写进去时测试必须变红，否则它就是又一个"永远通过的断言"（§4.71 / §4.73 有实录）。

### 5.2 dangerouslySetInnerHTML 只有一处，已防护 `[读码]`

`[grep]` 全仓只有 `RichText.tsx:126` 一处 `dangerouslySetInnerHTML`，用于 HTML payload 预览。README 写明走 DOMPurify + `sandbox=""` iframe。这是正确的防护——**无需行动，仅确认**。

### 5.3 fs:default 权限较宽 `[文档]`

AGENTS.md 把收窄 `fs:default` 列为属主决定。提案 S2 给了实施顺序：先加 `write_text_file` 后端命令 → 改 `exportMessages.ts` 走它 → 再删 `fs:default`。**顺序不能反**——先删权限等于静默砍掉导出功能。

## 6. 测试与门禁

### 6.1 门禁纪律是项目最大的资产 `[文档]`

CI 四作业（frontend / ui / backend / cli）+ 本地门禁脚本（i18n parity / release-ready / release-shipped / ci-shell / bench-history-lock）+ ESLint 恰好 10 warning 预算 + clippy `-D warnings`。**这套门禁的强度在单人项目里极其罕见**，而且项目自己记录了两次"永远通过的断言比没有断言更危险"的教训（§4.71 / §4.73），说明门禁本身也被审视过。

### 6.2 核心状态机覆盖不足 `[读码]`

`mqtt_manager.rs` 3759 行 / 6 条单测（§4.1）。依赖 `AppHandle` 的模块（`bridge.rs` / `mqtt_manager.rs` / `lib.rs`）进不了 harness，只能靠真机端到端覆盖。提案 O5/O6 的建议是对的：把"某主题是否应在本次 ConnAck 重放"这类判定抽成不依赖 `AppHandle` 的纯谓词，让决策与副作用分开。**这是工程质量里最值得投入的一条。**

### 6.3 变异测试已手工证明价值 `[文档]`

§4.80 / §4.81 / §4.82 / §4.85 每次手工变异都抓到了洞。提案 T2 建议把手工变异半自动化——先做一个最小脚本对指定常量/布尔做机械变异、跑指定测试、报告"哪些变异没被杀"。**同意**，这比"每次靠记性做一遍"可靠。

## 7. 我的独立见解（提案未覆盖或角度不同）

### 7.1 "诚实"是产品定位，不只是工程纪律

项目最独特的资产不是任何一个功能，而是**贯穿全局的"诚实"**：投递审计说"不在我们已存下的内容里"而不是"broker 丢了"；TLS 报告对未知问题码原样显示；CLI 有退出码 4"未证明"；面板后端返回 null 时说"需要桌面端后端"而不是渲染一份空报告。

提案 I6 建议把这升格为统一的 `Verdict` 对象（`proven / violated / not_proven / unknown_because`）——**这是六个创新点里最便宜且是其他创新点地基的一条**。我额外补充：**指标端点可以暴露"未证明结论的数量"**，这是一个别的工具连概念都没有的指标，且完全符合脱敏约束。

### 7.2 控制台分 tab 比"藏起来 + 命令面板补救"更治本

见 §1.1。提案把发现性问题归结为"capabilities 藏在折叠面板里"，解法是命令面板。我认为更治本的解法是控制台内部分 tab（收发 / 观测 / 仿真·验收），让每个 tab 的信息密度可控。命令面板仍然有用，但它应该服务于"我知道我要什么，帮我跳过去"，而不是"我不知道有什么，帮我发现"。

### 7.3 桌面应用的窗口尺寸适配被低估了

README 强调"fluid container-driven layouts"，但固定 240px 侧栏 + 无响应式断点 + 控制台 12 面板纵向堆叠，意味着**窄窗口和矮窗口的体验都没被设计过**。对一个常被缩到半屏对照日志的运维工具，这是真实场景。低成本改进：侧栏折叠态 + 控制台分 tab。

### 7.4 后端无日志是 I7 的前置，也是 console.error 的根因

`[grep]` 后端零 `tracing` / `env_logger` / `panic::set_hook`。前端 ~20 处 `console.error` 是因为没有后端日志可走。I7（应用自身的失败可见性）应该**排在很多功能之前**——因为它是一个"让其他 bug 能被发现"的元能力。一个 panic 后用户只拿到 OS 那句"已停止工作"，这和项目"失败不许看起来像成功"的哲学直接矛盾。

### 7.5 提案的排序我基本同意，有一处调整建议

第一批提案 §5 的排序是：I6 → I3 → R1+R4 → O2+O9 → I1 → I5 → I2 → I4。

**我的调整**：把 **I7（应用自身失败可见性）** 提到第 2 位，紧跟 I6。理由：
- I7 是"元能力"——它让其他问题的诊断变可能。
- 它的硬约束（日志脱敏）恰好可以复用 I6 的 `Verdict` 思路，两者天然同路。
- 它的成本是中等的，但"把哲学用在自己身上"的价值最高。

另外，**V1（两实例互踢）的验证**应该排在最前面——它成本极低（起两个实例读 clientId），且如果成立，是一个真实的正确性问题。
