## 1. 创新点

### I1 · 设备行为基线 + 偏离检测

**它回答一个所有 MQTT 客户端都答不了的问题：这台设备还在发消息，但它发的东西变了。**

现在的看门狗（§3.4）回答的是"它是不是不说话了"。静默之外的另一半故障——**固件升级改了 payload  
schema、单位从 ℃ 换成 ℉、字段从数字变成字符串、上报周期从 5 s 漂到 40 s**——全部静默通过，  
因为消息还在来，人看到的只是"列表里多了一些行"。

**从历史自动学出的基线**（每条都对应一个已有的取证能力，不是新造概念）：

| 维度         | 从哪来                                                    | 偏离怎么判                                             |
| ---------- | ------------------------------------------------------ | ------------------------------------------------- |
| payload 结构 | 历史 `payload` 列 + 已有的 JSON 路径遍历（`utils/messageDiff.ts`） | 键集增删、同路径类型变化（§4.81a 已经为"1 vs "1""打过补丁，那正是这类偏离的探针） |
| 数值值域       | `utils/fieldSeries.ts` 已有分位与断点逻辑                       | 超出历史分位区间，且**必须报样本量与观测窗口**                         |
| 上报周期       | `utils/deliveryAudit.ts` 已在算时延分位                       | 中位数漂移比例                                           |
| 传输属性       | 历史已有 `qos`/`retain`/`content_type`/`direction`         | QoS 或 retain 习惯变了                                 |
| 协议声明       | v5 properties 已入库（§3.8）                                | 发布方改了 PFI / content-type                          |

**为什么这属于"创新"而不是"又一个告警"**：它的结论是**学出来的**，因此必须自带诚实的边界——  
样本不足就判"未证明"而不是"正常"，观测窗口被保留策略裁过就要说，基线里混入过故障注入的流量  
就要标。这恰好是 I6 那套契约的第一个真实用例。

**导出成契约**：基线可导出成 JSON Schema，喂给 CLI 断言（`--assert schema:baseline.json`）。  
于是"设备改了 schema"从"人盯着看"变成 CI 里的一条断言。这也顺带让 §6.4 之外多了一条  
"协议语义不退化"的可回归证据。

**成本与风险**：中等。真正的风险不是算法，是**误报**——一台本来就该有多样性的设备会被判成  
反复偏离。第一版应该只报不拦，且每条偏离都要能"一键把它加进基线"。

### I2 · 反事实重放（Counterfactual Replay）

**一句话：同一段真实流量，改一个变量，跑 N 遍，看哪条断言从绿变红。**

MQTT 里最难回答的问题是"我把 QoS 从 0 改成 1 会怎样""这个 broker 换掉会怎样"。现在只能靠猜，  
或者靠在生产上试。三个零件仓库里**已经全都有了**，缺的只是把它们串起来：

- `.dqrec` 会话录制与按节拍回放（§4.59）
- `.dqscn` 验收场景：装置 + 判据 + 结论（§4.62）
- 故障注入（丢/延/重/篡改/错关联，§4.41）
- CLI 的 `verify --scenario` 与退出码契约（§4.70）

**形态**：一份录制 + 一个"变量矩阵"（`{qos: [0,1,2]} × {protocol: [4,5]} × {fault: [none, drop10%]}`），  
对每一格在一次性 broker 上重放并跑同一套断言，产出一张绿红矩阵。

**为什么值得做**：现有 CI 的四个作业证明的是"代码没坏"，没有一个证明"协议语义没退化"。  
`cli` 作业跑的是当前 broker 的当前行为；反事实矩阵跑的是**同一份流量在不同条件下的行为差异**——  
这是唯一能在 CI 里抓住"B2 那批 v5 属性在某条路径上悄悄失效"这类回归的形状。

**诚实要求（硬约束）**：矩阵每一格必须标注"这一遍的流量是**录制的**，不是现场的"，  
并且录制期间如果应用自己注入过故障，那个事实必须跟着录制文件一起存下来——  
否则一个"因为注入了 10% 丢包才红"的格子会被读成"这个 broker 有问题"。

**成本**：中等。最大的未知是回放的确定性：定时类场景（时间窗、超时、冷却）在压缩/加速回放下  
语义会变。第一版建议只支持**原速回放**，把"倍速"列为明确不做，理由写进文档。

### I3 · 保留值沿革 + 僵尸 retain 检测

**零协议改动，纯 SQLite 计算，但给出的是别人没有的结论。**

历史里每一条 `retain = 1` 的入站行，都是该主题保留值的一次变更。**这些行已经躺在库里了，  
没有任何客户端把它们当成"保留值的版本序列"在用。**

三个立刻有用的输出：

1. **保留值时间线**：某主题在什么时候被谁改成了什么，最后一次变更距今多久。
   - 空 payload + `retain=1` 是**删除**，必须标成终态而不是一个空值——否则时间线结尾会是  
     一片空白，读起来像"值没了但我们不知道为什么"。
2. **僵尸 retain 检测**：最后一次更新在 N 天前，但每个新订阅者仍会立刻收到它。  
   这是 IoT 里极常见的一类坑（一次性配置下发后忘了清），而且**只有能看历史的工具才看得见**——  
   连上 broker 的那一刻你只能看到当前值，看不到它有多老。
3. **"我们没在看的时候有人改过"**：把"历史里看到的最后保留值"与"现在订阅收到的实际保留值"  
   对比，不一致就说明变更发生在观测之外。这是取证级结论，且天然带免责（我们只证明我们看见的）。

**顺带解决 ROADMAP §2.3 的一半**：那条说"保留消息只从当前 500 行流里捞，无法查保留树"。  
完整的保留树勘查需要协议侧探测（贵）；**保留值沿革用的是已有数据，是更便宜的那一半**，  
可以单独先做。

**成本**：小。计算是纯查询，UI 可以复用 `FieldProbeCard` / `TimelineCard` 的形状。

### I4 · 端到端谱系（Lineage）：这条报文最后去哪了

现有的 trace（§4.50）跟的是**一个标识的一生**（跨主题、跨方向）。缺的另一半是  
**一条报文的因果后果**（跨系统）：

```
设备报文 devices/gw1/t (in)
   └─ 桥接规则 #3 命中 → transform 改写
        ├─ → 出站 broker B 的 edge/gw1/t       ✅ 已转发
        ├─ → webhook https://…/telemetry        ✅ 200
        └─ → 告警 sink                          ✗ transform 返回 null，丢弃
```

现在每一跳**各有日志**（桥接转发日志、outbox 状态、webhook 计数），但没有一条能把它们串起来的线。  
排障时的真实问题是"这条设备数据到底有没有进业务系统"，而这个问题今天要开三个面板、人肉对齐时间戳。

**落地形状**：给每条入站报文一个 lineage id，随 `bridge` / `outbox` / `webhook` / `responder`  
传递；outbox 现在按 `rule_id` 记账（§6.7 自己指出缺"哪个目标"这一维），加 lineage 正好顺便补上。  
UI 上点击一条历史行可以展开它的一生，包括"在第 2 跳被丢弃"这种终态。

**为什么是创新**：这是把"五个工作区"第一次变成**一条链**——文件传输之外的四个工作区今天  
是四个并列视图，谱系是它们之间缺失的那条边。

**诚实要求**：谱系中断的那一跳必须说清是"我们没记录"还是"确实没发生"。outbox 已经区分  
"失败"与"死信"，这个区分要一路带到 UI。

### I5 · 双 broker 一致性探针（不做完整多连接）

**这是对 §3.5「多连接」的一个折中提案，请优先于完整多连接评估。**

完整多连接的改造面已经量过（§6.3）：73 个命令隐含"只有一个连接"、`App.tsx` 单是  
`broker.isConnected` 就 23 处、事件名要分道、31 个 spec 的 mock 全改。这是一次架构改动，  
且要先拍板"现有 4.8 万行历史如何归属"。

**折中方案**：只加**第二个只读探针连接**（`probe`），它不参与任何现有命令的语义，只服务一个  
新面板——「一致性对比」：

| 对比项                 | 怎么测                         | 价值                   |
| ------------------- | --------------------------- | -------------------- |
| 订阅裁决                | 同一批过滤器各发一次，比 SUBACK 码       | 迁移后 ACL 漏配           |
| QoS 降级              | 发 QoS2 看回到什么                | 换 broker 后静默降级       |
| retain / 通配符 / 共享订阅 | CONNACK 能力表（§4.27 已有）+ 行为验证 | 新 broker 不支持         |
| 到达与时延               | 同一条报文各发一次，比是否到达与耗时          | fan-out 链路差异         |
| `$SYS` 指纹           | §2.1.5 已有厂商指纹               | 确认连的是不是自以为的那个 broker |

**真实场景**：broker 迁移、版本升级、换云厂商的验收。这是**企业用户会为此打开这个工具**的  
那一类问题，而 MQTTX 在"多连接 GUI"上的广度并不能回答它（那是多个并列连接，不是一致性对比）。

**为什么它便宜**：不触碰 73 个命令的语义，不触碰历史归属，不触碰事件名。新命令、新面板、  
新 spec，其余全部不动。桥接那套"任意 conn id"已经是现成的范本。

**诚实要求**：差异报告里每一条要能区分"broker 的差异"和"时序的抖动"——同一条判定至少重复  
三次，只在三次一致时才报为差异；否则报告本身就是噪声。

### I6 · 把"诚实"做成机器可读的契约

**这是本项目最独特资产的收口，也是六个创新点里最便宜的一个。**

现在的状态是**各处各自诚实**：

- CLI 有退出码 4「未证明」(§4.70)
- 投递审计有无条件常驻的免责行，且只说"不在我们已存下的内容里"(§4.81b)
- TLS 报告对未知问题码原样显示而不是消失(§4.82)
- 投递审计把"字符串序号"排除在序号之外，把负时延单独计(§4.81b)
- 面板后端返回 null 时说"需要桌面端后端"，不渲染成一份"检查通过"的空报告(§4.82)

但这些诚实**没有统一的形状**：无法聚合、无法做趋势、无法跨 UI/CLI/场景/指标复用。  
`verdict.rs` 已经存在（274 行），CLI 的退出码已经是这个思想的产物，缺的是把它升格为  
贯穿全局的**结论对象**：

```
Verdict {
  claim,                                  // 断言了什么
  status: proven | violated | not_proven | unknown_because,
  evidence[],                             // 支撑它的具体行/次数/时间
  sampleSize, windowStart, windowEnd,     // 结论的适用范围
  caveats[]                               // 无条件携带的免责，不是出错才显示
}
```

**收益**：

1. UI、CLI、`--junit`、`--json`、`/metrics`、导出的 trace HTML（§4.55）共用同一份结论对象——  
   现在它们各自拼字符串，语义漂移只靠人盯。
2. I1 的基线偏离、I3 的僵尸 retain、I5 的一致性差异，都能直接产出 `Verdict`，不需要各造一套措辞。
3. **指标端点可以暴露"未证明结论的数量"**——这是一个别的工具连概念都没有的指标，  
   而且完全符合现有的脱敏约束（指标名与标签里不出现报文/主题/clientId）。

**成本**：小到中。真正的成本不在代码，在于要把现有各处的措辞**逐条映射**到这四个状态上——  
这是一次需要逐个面板走的审计，值得单独一轮。

## 2. 需求点

### 2.1 便宜的 80%（小成本换大感知）

- **R1 保存的连接档位（profiles）**。  
  多连接的完整形态很贵，但用户真正的痛点常常只是"我有开发/测试/生产三个 broker，别让我每次重填"。  
  形态：N 个命名配置 + 快速切换 + 导入导出（**脱敏沿用 §4.44 环境包那套，不导出密码——  
  密码已经是 `secretRef`，本来就不在本地配置里**）。改造面只是设置面板 + 一个 localStorage 段，  
  不碰命令语义。**建议它排在完整多连接之前。**
- **R4 定时任务持久化 + 启动时恢复**（C2b，§6.5）。现在任务只在会话内存活（§5.6）。  
  顺带把"场景/环境包启动时自动装载"一起做——这两件事是同一个"启动态"概念。
- **R5 按规则的显式代理开关**（§6.8）。§4.74 已经证明"文档说直连、代码走代理"这类  
  说做不一会被自己坑一次，这条属于明确的欠账。
- **R9 PING 改成真 keep-alive 延迟**。ROADMAP §2.3：`mqtt_manager.rs:279-310` 现在测的是  
  CONNECT 握手 RTT，不是 keep-alive 延迟，且不周期刷新。这是社区最大的一组未解 bug，  
  而修复成本主要是一个周期测量 + 一个环形缓冲。
- **R7 历史库运维**：库在哪、多大、能不能搬、能不能手动 VACUUM。  
  现状是 WAL + 10 万行上限（[读码] `history.rs:20 MAX_HISTORY_ROWS = 100_000`）+ 按天保留  
  （[读码] `trim()`），但用户在界面上看不到"我的库现在多大、被裁掉了多少"  
  （`pruned_rows` 有记账，[读码] 但没有出口）。

### 2.2 补短板

- **R2 保留消息勘查**。ROADMAP §2.3：保留消息只从当前 500 行流里捞。  
  完整保留树探测要协议侧支持（mosquitto #1225 是长期未满足需求），做之前建议先看  
  I3（保留值沿革）——它用已有数据覆盖了一半价值，成本是 I3 的零头。
- **R3 断点续传**（§6.13）。`confirm_timeout` 后只能整笔重发。协议要加"从第 N 片继续"以及  
  "接收端如何证明自己还留着半截临时文件"。**没定协议之前不要做半成品**，这条我同意现状判断。
- **R6 一问多答收集模式**（§5.8 第 1 条）。现在第一条匹配上的应答就终结调用。  
  广播式收集是另一种设计，要做就做成显式模式（收集窗口 + 应答计数），  
  不要把它塞进现有的一问一答里。
- **R8 入站主题别名线上取证 + user-property 字节级复核**（§6.4）。  
  现在入站别名的依据只有 rumqttc 源码（§4.9 明确写了"这不是跑出来的"）。  
  项目里有现成的 golden sink 网（§4.47），这条应该很便宜。
- **R10 CLI 补齐 bench / 历史查询**。CLI 与桌面端共用同一套引擎（这是它存在的理由），  
  但 `bench` 和 `query_history` 目前只有 GUI 入口。补上之后 CI 能断言的东西多一大块。

### 2.3 收尾与欠账

- 多 sink fan-out 的 outbox 记账（§6.7 自己指出缺"哪个目标"一维）— 与 I4 的 lineage 天然同路。
- `bridge.rs` 的自动化回归（§6.10）：它只被真机端到端覆盖过一次，没有可重复回归。  
  但有 `#[cfg(test)]`（[读码]），说明抽纯函数这条路已经开了一个头。
- `ErrorBoundary` 的 Playwright 用例（§6.11）。

## 3. 优化点

> **前四条是性能假设，按 AGENTS.md 的规矩，动手之前必须先 A/B 量。**  
> 本项目已有两次"看起来该优化"量下来不是瓶颈的记录（§1.6、§1.12），别做第三次。

### 3.1 性能（先量后改）

- **O1 桥接每消息克隆 rules/conns 表**（§1.6）。评审称是最大可优化项，但从未量过。  
  建议：先用 `bench` 打一条规则的高速率流量，量出克隆在总耗时里的占比，再决定。
- **O2 历史查询的三处具体形状** `[读码]`
  1. `series()`（`history.rs:522`）**没有 LIMIT**，而 `query()`（`:448`）钳在 2000。  
     在"全部时间"窗口下，列表最多给 2000 行、图表扫全部 10 万行——  
     两者给出的**总数会不一致**。这正是 §2 P1"列表与趋势图对不上"那个已修问题的残留分支，  
     只是这次差在 limit 而不是谓词。建议：要么给 series 同样的截断并在 UI 上标出，  
     要么让两者共用一个"结果集上限"常量。
  2. 索引现状是 `idx_messages_ts(ts DESC)` / `idx_messages_topic(topic)` / `[读码]`  
     `idx_messages_corr(correlation)`。查询总是 `ts 区间 + (topic LIKE OR payload LIKE) + direction`，  
     缺一个 `(ts DESC, topic)` 复合索引；`direction` 没有单独索引。
  3. 搜索是 `%term%` 双侧 LIKE（`search_pattern`，`history.rs:861`），索引用不上。  
     便宜的改进：topic 前缀类搜索（`term` 不以通配符开头时）走 `topic >= x AND topic < y`  
     的范围扫描，能吃上 `idx_messages_topic`。**全文检索 FTS5 仍然建议不做**——  
     §4.38 的理由（写入放大在万级/s 是净损失）至今成立。
- **O3 前端 13 个轮询定时器** `[读码]`。`useTopicStats` 1 s、`useBridge` 两个（1.5 s 与 2 s，  
  **同一个 hook 里两个 timer**）、`useAssertions` / `useRpc` / `useFaults` / `useResponder` 各 1 s、  
  `useDiagnostics` 15 s、`useHistoryCount` 4 s/20 s、`HistoryPanel` 3 s、`useSubscriptionStats` 1.5 s。  
  假设：不可见工作区的轮询仍在跑，且没有统一的节流/合并。  
  **先量**（DevTools 数 30 秒内的 invoke 次数与主线程占用），再决定是不是要做  
  "按可见性降档 + 单一调度器"。
- **O4 bench 不镜像 feed/历史的开关**（§6.2）。§5.5 已经把预期校准过了：  
  它换来的是从 ~3000 往上，不是从 92 往上。按校准后的预期评估性价比。


### 3.2 工程质量

- **O5 `mqtt_manager.rs` 3732 行只有 6 条单测** `[读码]`。  
  这 6 条（`topic_traffic_*` ×3、`sanitize_*`、`get_unique_path_*`、`transfer_id_charset_*`）  
  都在文件末尾，覆盖的是流量统计与路径清理。**订阅隔离/重放（§4.85 刚出过 bug）、  
  feed 归档队列（§3.3 A2）、传输状态机（§4.13 出过竞态）这三类恰好是历史上真出过问题、  
  又恰好没有自动化回归的地方。** §4.85 那次"误删 257 行测试靠 `cargo test` 从 381 掉到 371 才暴露"  
  说明门是有效的——但门只守着它守得住的地方。  
  建议：把"某主题是否应在本次 ConnAck 重放"这类判定抽成不依赖 `AppHandle` 的谓词（同 O6）。
- **O6 依赖 `AppHandle` 的模块进不了 harness**（§4.1 / §6.12）。  
  `bridge.rs` / `mqtt_manager.rs` / `lib.rs` 只能靠真机端到端覆盖。  
  §6.12 的提议（把"条目能否被这次 finalize 广播"做成纯谓词）是对的，  
  而且它和 O5 是同一件事：把决策与副作用分开。
- **O7 i18n `types.ts` 1043 行手写接口可以派生** `[读码]`。  
  现在是 `en/zhCN/zhTW/ja` 四份 1032 键 + 一份手写 `Translations` 接口，共五处要同步。  
  `types.ts` 的键都是 `string`，没有结构嵌套以外的信息量——可以改成  
  `export type Translations = typeof en;`，parity 脚本改成"其余三份对齐 `typeof en`"。  
  少一处手工维护，且消除"接口写对了但四份文件漏一个"这类错误的一半来源。  
  （注：这是维护成本优化，不影响现有的 parity 门禁强度，改完要重跑脚本确认它仍然能抓到漏键。）
- **O8 79 个命令的手写 IPC 双份**。AGENTS.md 已列为"留给你决定"。  
  如果不想上 `ts-rs` 全量类型化，有个更便宜的形态：**只生成一份  
  `命令名 → (参数名, 返回类型)` 的清单**并由 CI 校验它与 Rust 侧一致，  
  不改动任何调用点。这能抓住"改了 Rust 签名忘了改前端"这一整类，  
  成本是全量方案的一小部分。
- **O9 门禁数字散落在两份 README 且已经不一致** `[读码]`。  
  `README.zh-CN.md:146` 写"Rust 381 lib、前端单测 225、i18n 1010 键"；  
  `docs/PROJECT_STATUS_2026_10.md` 写"383 / 231 / 1032"。  
  两处都是手写的，一定会再次漂移。建议：让 README 那一行由脚本生成（或干脆只留一句  
  "见 PROJECT_STATUS"），因为**一个对不上的数字和一个跑不起来的检查一样，  
  报出的"无事发生"长得和真的一样**（§4.84 的教训）。

### 3.3 门禁

- **性能回归门禁**：把 bench 的 p95 / lost 断言接进 CI。  
  风险是 flaky（CI 机器噪声大），建议第一版**只报警不阻断**，  
  并且——沿用 §4.84 的思路——**先用一个已知的劣化验证它真的会红**。
- **反事实重放进 CI**（I2 的工程化）。这是唯一能证明"协议语义没退化"的门。
- **发布产物冒烟**：`check-release-ready.py` 已经覆盖了发版才走到的路径（§4.84）。  
  §5 手工做过"启动 release exe 读一次 `/metrics`"，这件事可以脚本化成发布后的最后一道检查。

### 3.4 正确性

- **O10 `refuse_oldest_pending_sub` 可能怪错主题**（§4.85 挖出、主动未动）。  
  多个 SUBSCRIBE 挤在一起时，错误码被归因给"最早在飞的那个"；被误怪的好主题会被隔离、  
  从此不再重放。项目自己写明"风险与收益不匹配"——我同意不动，  
  但建议至少加一条能失败的测试把现状钉住，否则它会在某次改动里被顺手改坏。

## 5. 建议的下一轮排序

排序原则：**先把"便宜且收口"的做完，再动架构项。**

1. **I6 不确定性契约**（小成本，且是 I1/I3/I5 的地基）+ **O7 i18n 派生**（半天）
2. **I3 保留值沿革 + 僵尸 retain**（小成本，用已有数据，直接回答一个真实问题）
3. **R1 连接档位** + **R4 定时任务持久化**（都是"启动态"这一族，感知强、改造面小）
4. **O2 历史查询三处** + **O9 数字单一来源**（先量，再改）
5. **I1 设备行为基线**（中等，需要专门一轮，因为误报是主要风险）
6. **I5 双 broker 一致性探针**（中等，但**建议排在完整多连接之前**——它是同一需求的更便宜形态）
7. **I2 反事实重放**（中等，依赖录制回放的确定性，需要先做个可行性验证）
8. **I4 谱系**（中等，与 outbox 的"哪个目标"这一维同路，可以一起做）

**仍然建议留给属主拍板的**（沿用 AGENTS.md 的清单，本文不替你决定）：  
完整多连接、`releaseDraft`、收窄 `fs:default`、历史双 payload 列、typed IPC、  
`-core` 版本后缀、`tsconfig.node` strict。

**本文明确不建议做的**（理由与项目既有判断一致）：  
前端虚拟化（§4.53 实测更慢）、历史 FTS5（§4.38）、Web 版 / 云同步 / AI Copilot /  
独立设备模拟器 GUI（ROADMAP「明确不做」）、在协议未定时做断点续传半成品。

## 6. 验收口径（沿用本仓库既有标准，不另立）

每一项落地都要同时满足：

- Rust：`cargo test` + `cargo clippy --all-targets -- -D warnings`
- 前端：`tsc --noEmit` + `vitest` + `playwright` 全绿；ESLint 仍在 10 条 warning 预算
- i18n：四语言等键 + `scripts/check-i18n-parity.py`
- 真机：一次性 broker（`scripts/gate-rig.sh`，**不碰 1883**）跑一遍真实链路
- **语义类改动必须有线上或可观测证据**，不接受"界面显示了"即算通过
- **性能类改动先 A/B 量出数字**，不允许用推理替代实测
- **新加的断言要被变异测试验证过**：改动对应的行为被破坏时，测试必须变红
